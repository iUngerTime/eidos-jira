## Jira

Jira is a plugin from outside the package (`@iungertime/jira`) that connects a root to Jira Cloud boards. Each connection is one board or project with one direction; pull brings Jira's issues into the Backlog as tasks, and their comments as Comments threads. A person is written as the root user of the same name where the root has one (or the one the mapping's `users` names), else as Jira names them. With `add_people` on (a root setting, off by default) a pull adds each person the root does not have to its users, and a fetch lists them (`@` lines). The root of blueprints stays the source of truth for everything the mapping leaves alone; at a pull, Jira wins on every field the mapping carries that the root does not own. A pulled task's changes go back one issue at a time with `sync`, which settles each field against what both sides held at the last pull or sync and stops on anything changed in both; `create` makes an issue from a task. Nothing is sent to Jira on its own.

### Files

- `.eidos/plugins/jira/settings.yaml`: `connections` (shared), each `{ name, site, project, board?, jql?, direction, restricted_comments?, mapping }`, and `pull_attachments`.
- `.eidos/plugins/jira/local.yaml`: `accounts`, the email each site signs in with for this root; `auto_fetch`; `auto_sync_on_save` and `auto_sync_on_push`, each person's auto sync (off by default), which runs only where the app is open and leaves anything to settle in `local/needs.json` (the sidebar's Needs you). Never committed.
- `.eidos/plugins/jira/local/`: what `describe` read per connection, and the last pull's time. Never committed.
- A pulled or created task holds its issue in its frontmatter, `jira: { site, id, key, updated, comments, parent?, digest, remote, connection?, gone? }` (`digest`: what the task held at the last pull or sync, per field; `remote`: Jira's own value then), written by the plugin alone; never edit it. A create cut short leaves `jira: { site, connection, pending, since }` until the next create of that task finds its issue.
- `.eidos/plugins/jira/local/sync/<issue id>.json`: a sync cut short; `eidos jira status` names it, the next sync of that issue finishes it.
- The API token is in `plugins/jira/credentials.json` in the Eidos app data folder, readable only by its owner, never in the root or a settings file.

### Commands

- `eidos jira login <site> [--global] [--email <email>]`: asks for the email and the API token (hidden; read from stdin without a terminal), checks them against Jira, keeps them; `--global` makes the account the default for every root, otherwise only this root uses it. A machine may keep several accounts for a site: `use <site> <email> [--global]` picks one for this root or as the default, `logout <site> [--email <email>]` signs out one or all, `whoami [--json]` says which this root uses.
- `eidos jira connect <name> --site <site> --key <KEY> [--board <id>] [--jql <jql>]`, `disconnect <name>`.
- `eidos jira describe <connection> [--refresh] [--json]`: the board's columns, issue types with statuses and fields, priorities, link types, sprints.
- `eidos jira map <connection> [--yes] [--json]`: a mapping drafted by names and categories; in a terminal each entry is asked, `--yes` accepts all, `--json` prints the draft (`{ entries: [{ part, jira, eidos, why }], unmatched: [] }`).
- `eidos jira configure:map <connection> set|unset <part> <from> [<to>] [--types <a,b>] [--push] [--owner jira|eidos]`: one entry; parts are `types`, `statuses`, `priorities`, `link_types`, `fields` (`{ jira: <field id>, eidos: title|status|priority|assignee|milestone|parent|property:<name>|section:<key>, types?, owner? }`), `users` (`{ jira: <account id, email, or Jira name>, eidos: <root user> }`), `parent` (`subtasks`, the default: only a Jira sub-task becomes a Backlog subtask; `all`; `none`), `transition_fields` (`set transition_fields "<Jira status>" <field>=<value>`: what that transition's screen is sent, as `resolution=Won't Do`), `create.types` (`set create.types <Backlog type> "<Jira type>"`), and `create.fields` (`set create.fields <field id> <value>`: a default for a field Jira requires on create). `--types` makes a field pair hold for those issue types alone, beside or in place of the field's pair for every type: an epic's field can go somewhere a bug's does not. `--push` marks the Jira value a sync or a create sends where several read as one Backlog value (Done, not Canceled). `--owner eidos` makes a field the root's: a pull never overwrites it and a change in Jira to it is a conflict at the next sync; `--owner jira` makes it never sent. The first entry of a part a connection did not hold makes that part carry only what it names (the command says so): draft the whole part with `map` before marking one entry of it. `--also` adds a section beside the ones a rich-text field already goes to rather than replacing them (on a connection naming no fields, beside the default fields): Jira holds the bundle as one text, the first section's, then each other under a `## <section title>` heading, a checklist as a task list; a pull splits it at those headings, and a section whose heading Jira's text lacks is left as the root has it. `unset fields <field> <section> --also` takes out that section alone. Keep a section out of every field (Implementation Plan, Implementation Notes) by mapping it nowhere.
- `eidos jira fetch [<connection>] [--full] [--json]`: what a pull would do; writes nothing to the root. JSON: `[{ connection, since, add, change, local, comments, people, gone, back, left_out, attachments, milestones, unchanged }]`.
- `eidos jira pull [<connection>] [--dry-run] [--full] [--keep-local] [--json]`: does it. JSON: `[{ connection, added, changed, kept_local, comments, people, gone, attachments, left_out }]`. A fetch also lists `owned`: tasks whose root-owned fields Jira changed, left for a sync (`⇄` lines).
- `eidos jira status [<connection>] [--json]`: from the root alone, no request to Jira: the tasks edited here since their last pull or sync and which fields (`~`), the creates and the syncs cut short (`…`). JSON: `[{ connection, edited: [{ task, key, sides }], pending: [task], interrupted: [{ key, at }] }]`.
- `eidos jira sync [<task>...] [--connection <name>] [--dry-run] [--take <field>=jira|eidos]... [--accept-loss <field>]... [--status-to <Jira status>] [--via <s1,s2>] [--field <field>=<value>]... [--no-comments] [--yes] [--json]`: each task and its issue brought level. Per field: `←` from Jira, `→` to Jira, `=` the same on both (settled, nothing sent), `!` changed on both (a conflict), `✗` what stops the issue with its `fix:`. An issue with anything marked `✗` is not synced at all. `--take` settles a conflict (`all` for every field); `--accept-loss` agrees to a text write that takes out of Jira what markdown cannot hold (a panel, a file whose block was rewritten); `--status-to` picks among Jira statuses that read as the task's; `--via` walks a status more than one transition away; `--field` answers a transition's screen. Without a terminal it writes only with `--yes`. JSON: `[{ plan: { task, key, url, fields: [{ side, jira, verdict, eidos, remote, reason?, kept? }], status, comments, blockers: [{ side, code, message, fix }], loss, level }, done, skipped? }]`.
- `eidos jira comment <task> <text...>`: a comment sent to the issue now as the account you sign in with, kept in the issue's thread here.
- `eidos jira create <task>... --connection <name> [--type <Jira type>] [--field <field>=<value>]... [--again] [--yes] [--json]`: an issue made from each task, its plan shown first (type, values and where each came from, parent, `✗` what stops it). A batch with any task stopped makes nothing. The issue starts in its workflow's first status; the next sync sends the task's. `--again` creates anew a task whose cut-short create's issue cannot be found after a few minutes.

### Setting a connection up, or changing it

The Backlog comes first: Jira's values map onto what the Backlog declares, so it needs its statuses, task types, priorities, and link types before a board is mapped. In the app, the person does all of this from the plugin's settings page (Mapping…); from a terminal, walk it with them:

1. Read both sides. The Backlog's: `eidos backlog types --json`, `properties --json`, and `link-types`, and its statuses, columns, and priorities in `.eidos/plugins/backlog/settings.yaml` (its defaults where that file leaves them out); `eidos jira describe <connection> --json` for Jira's (`--refresh` after the board changed).
2. Propose each part as a table, a row per Jira value and the Backlog value it would go to, and let the person change any row before you write it: issue types (a sub-task type usually to the default type, filed by the parent rule), statuses (by name, else by category; any status may go anywhere, an Intake to Done included), priorities (by name, else by rank from the highest), link types. `eidos jira map <connection> --json` gives a draft to start from. A value the Backlog lacks is added there first (`eidos backlog configure:status add …`), not left out silently.
3. Fields per issue type. The issue types do not share their fields: look at each type's list in `describe`, and where a field means something different per type (a story's points, an epic's target date), write a pair per type with `--types`. A field with nowhere to go gets a property, declared with `eidos backlog configure:property add <name> --type <type>` and, for a Jira field with a closed set, `--options` holding Jira's values: Number for a number, Date or Date & time for a date, List for an array or the sprints, Text otherwise (with options for a single choice).
4. Check it. `eidos check` reports each problem the mapping has as a `jira/` finding (a pair whose field cannot be carried there, an option the property lacks, a target the Backlog does not declare); fix every one. Then `eidos jira fetch <connection> --json` and show the person what a pull would add and change.
5. Ask before anything is pulled. After a mapping changes on a connection that has pulled before, pull with `--full`.

### Working it as an agent

Fetch before you pull and show the person what the fetch found, above all the tasks it names as edited here (`!` lines): a pull overwrites those fields unless `--keep-local` is passed, so when the person wants their edits in Jira, sync those tasks first. Never edit a task's `jira` key. Run `--full` after a mapping changes, since a pull otherwise reads only the issues Jira changed.

Sending to Jira is the person's call, every time. Run `sync --dry-run` (or `create` without `--yes`) and show them the plan; settle every `!` and `✗` with them, never choosing a side, a status, a resolution, or a loss on their behalf; pass `--yes` only once they agreed to that plan. A comment you write is never sent: only the person's own messages are, since Jira records them as the person's account. `eidos jira status` tells what is waiting without a request to Jira.
